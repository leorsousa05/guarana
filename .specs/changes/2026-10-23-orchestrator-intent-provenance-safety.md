## Historical planning correction — documented V2 setup contract (2026-10-23)

The official [OpenCode V2 plugin documentation](https://opencode.ai/v2/docs/build/plugins/) (Sessions section / SessionContext reference) describes the plugin context as the API client itself and exposes `ctx.session.get({sessionID})`. Current `setupGuaranaOrchestrator` passes `{ client: ctx.client }` into `GuaranaOrchestrator`; the V2 setup regression's `mockContext` instead models nested `client.session.get`, so it does not represent the documented context shape. The authorized `lookup-unavailable` probe means `client?.session?.get` was not callable in the V2 prompt hook. This confirms the V2 adapter-contract mismatch at the setup boundary and explains the unavailable lookup; it does not independently explain the inconsistent outcomes of earlier live Task runs.

The planned correction was subsequently implemented: documented top-level `ctx.session` is wired into the existing metadata lookup, the setup fixture uses top-level `session.get` with no `client` property, and the agentless child lookup retains the existing `{sessionID, directory}` arguments and workflow-byte/state, no-bootstrap, and no-parent-injection safeguards. ## ADR-039 explicit plugin-adoption CLI (2026-10-23; offline implementation verified)

The user accepted the explicit offline command `guarana plugin adopt <plugin-file> --accept-current [--project]` to reconcile one of the three allowlisted Guarana plugin filenames in the selected scope. It requires explicit acknowledgment, a valid existing manifest with exactly one valid tracked entry, an existing regular non-symlink target, the recognized plugin-specific marker, and current bytes with a SHA-256 different from the tracked hash. Success changes only that entry's hash in the selected install manifest; plugin bytes and all unrelated manifest groups/entries remain unchanged. A single-target manifest transaction must roll back on ordinary filesystem errors.

Missing acknowledgment, unknown plugin, absent/malformed manifest or entry, duplicate/invalid entry, equal hash, missing/symlink/non-regular target, or missing marker must reject without writes. Normal install/uninstall preflight remains unchanged and strict; a standard install can proceed after adoption via that existing guard.

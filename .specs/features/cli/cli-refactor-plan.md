## Goal
Record a complete, phased, behavior-preserving plan to refactor the Guarana CLI without implementing code or changing behavior during planning.

## Requirements
- Target architecture: retain bin/guarana.js as a thin entry point delegating to cli/main.js; replace eager command imports and ad hoc dispatch with a command registry and metadata; establish consistent parser, handler, result, error, and I/O context contracts; separate lifecycle and artifact-ownership services; keep domain handlers bounded.
- Phase 0 — characterize before migration: inventory every existing command and subcommand and document observable argv handling, help/version, output, exit codes, global versus nested flags, async behavior, target paths, and ownership behavior; add missing main-dispatcher characterization coverage. Exit gate: tests cover the current command/subcommand matrix and important contracts, with migration notes for each.
- Phase 1 — dispatch and parsing: finish parser and registry/help metadata using a single help source, with coverage for every documented form including `memory compact` and `specs record --file`. The bounded help-metadata slice introduces a dependency-free metadata source consumed by both command registry (preserving the same command names and handler mapping) and help rendering; global help and detailed `memory`/`specs` help use shared usage/subcommand definitions. It must preserve dispatch and accepted syntax without parser or behavior changes. The already completed registry-only and argv-helper slices are historical and independently bounded: they preserve the behavior present at the time, including the memory-search parser collision. The selector-position correction subsequently implemented the accepted project-selector contract below while preserving the other existing `--project` forms, and independently passed verification. The earlier ADR-031 write denial under the prior permissions is historical; after permission-profile confirmation, a fresh user-authorized attempt appended ADR-031. This supersedes only the current no-retry hold; final independent CLI verification remains pending. Exit gate: complete command/subcommand/flag coverage, including the dual selectors in `guarana --project memory search --project HASH`; metadata/registry consistency and shared-help coverage tests pass; `node --test cli/main.test.js cli/commands/memory.test.js cli/commands/specs.test.js` and `npm test` pass; no new dependencies.
- Phase 2 — process, I/O, and errors: establish one uniform awaited command invocation, result, error, stdio, and exit-code contract at the CLI boundary; remove command-level `process.exit` while preserving current outputs/codes and web child-process/signal behavior. Exit gate: contract tests establish consistent success/failure behavior and migrated commands retain their characterized documented behavior. The bounded execution-boundary slice changes only `cli/main.js`, `bin/guarana.js`, and `cli/main.test.js`; command-specific migration remains deferred. Its independent verification and corrected scope are recorded in criterion 27.
- Accepted bounded command-migration slice: change only `advisor.run` and `specs.run` to return explicit numeric zero or one instead of mutating `process.exitCode`, preserving current JSON/human output and diagnostics. Apply the command-specific return outcomes and tests in criterion 28. Do not migrate other commands or remove `cli/main.js`'s legacy adapter in this slice; preserve existing bin exit statuses, behavior, and dependencies.
- Next accepted bounded command-migration slice: migrate only memory failure paths in `cli/commands/memory.js` to throw validation, engine-missing, and domain errors to the existing central boundary, while preserving exact stderr text and status. Unknown memory subcommands retain their existing diagnostic on stderr, print detailed memory help on stdout, and return 1. Help and successful commands remain status 0. Add spawned CLI failure tests for representative missing-vault and invalid-argument cases and unknown subcommands, plus an assertion that memory contains no `process.exit` or `process.exitCode`; do not duplicate diagnostics, edit other commands, or add dependencies. See criterion 30.
- Next accepted bounded Phase 2 numeric-result slice: all nine registered command handlers return an integer from 0 through 255 on every normal or explicitly handled path, including help and handled failures. Operational failures may throw/reject and `cli/main.js` converts them to status 1. The main boundary treats an undefined, non-integer, or out-of-range result as a contract error and returns 1; it has no `process.exitCode` fallback. Only `bin/guarana.js` mutates `process.exitCode`. Preserve output, established exit codes, async behavior, and CLI status; add no dependencies and do not change project semantics. Acceptance and verification remain pending under criterion 37.
- Phase 3 — lifecycle and artifact ownership: separate install, update, uninstall, and plugin lifecycle orchestration from path resolution, ownership checks, and file operations. Reconcile conflicting copy semantics. Exit gate: project/global target paths remain stable and regression tests prove foreign files are never overwritten or removed, including partial failures. The code-path-confirmed plugin install/uninstall deletion issue and its preflight/ownership-manifest mitigation are tracked in [known issues](../../state/known-issues.md#2026-10-10--plugin-installuninstall-can-delete-foreign-target-files); runtime reproduction is not claimed.
- Accepted first Phase 3 implementation slice (Phase 3a) — safe managed-tree operations and per-scope manifest support for memory, orchestrator, and skill engines, integrated with plugin install/uninstall. Use one manifest per scope: project `.guarana/install-manifest.json`; global `$XDG_CONFIG_HOME/guarana/install-manifest.json`, falling back to `~/.config/guarana/install-manifest.json`. Record managed relative paths and SHA-256 hashes. Preflight ownership before mutation; preserve untracked extras; overwrite or delete manifest-owned files only when their current hash matches the recorded hash, otherwise refuse and preserve locally modified files. Legacy adoption is allowed only with existing proof: skill stamp/root Guarana metadata; plugin/profile markers; or, for an engine directory, a corresponding existing Guarana-owned sibling plugin proving association. For legacy directories touch only known bundle paths, preserve extras, and refuse ambiguous engine directories without proof. Memory vault and Advisor settings remain outside uninstall inventory. Plugin install/uninstall must preflight engine ownership before plugin changes, merge known files rather than recursively remove directories, track hashes, preserve extras on install/update/uninstall, and remove directories only when empty. Preserve CLI output, target paths, and dependencies. This Phase 3a slice is not a full lifecycle transaction; follow-up artifacts and rollback are separately scoped. The earlier ADR edit denial under prior permissions is historical; a fresh user-authorized attempt after permission-profile confirmation has appended ADR-031.

# Feature spec: Dashboard page-flow rework

**Status: VALIDATED**

## Goal
Substantially rework Dashboard page structure and end-to-end flows to reduce navigation and click depth, consolidate related content, and use dropdown subitems, progressive disclosure, and graphical/visual summaries while preserving current capabilities, routes, and contracts.

## Requirements
- Organize the Dashboard around three primary workspaces: Operation, Knowledge, and Settings. Operation has an integrated “Now” landing combining relevant Overview, Activity, Workflow, and Runs signals; Knowledge is a hub/search across Specs/documents, Memory, and Skills with source and scope clearly labeled; Settings provides internal direct navigation among Models, automation/workflow preferences, and dashboard preferences.
- Treat all workflows as priorities. Use dropdown subitems, progressive disclosure, and graphical/visual summaries to reduce navigation depth and consolidate related content. Preserve useful details as contextual destinations or subviews; do not hide capabilities or collapse everything into one giant page.
- Retain current page content and functions: Overview's active workers, Advisor, injection, and scoped graphs; Activity's workers, sessions, timelines, and workflow context; Runs' filters, history, and event modal; Workflow's phase and details; Specs' decisions, roadmap, state, and Documents tab; Memory's separate Project knowledge and global User preferences with nested tabs; Skills' Global and Project scopes; and Settings' Models, scoped workflow preferences, and scoped web preferences.
- Retain the Fieldstation shell visual identity. This task changes page information architecture and content flows, not the shared shell design.
- Preserve local-only Dashboard security and selected-project boundaries. Follow ADR-041: project roots are server-side allowlisted, browser data uses opaque project IDs and safe names, and browser-supplied paths do not grant filesystem authority. Use selected-project endpoints for project data.
- Preserve ADR-033's independent existing web, workflow, and Advisor settings files and formats, project-over-global resolution, and source labels; do not migrate or overwrite settings. Keep project Memory separate from global preferences and keep global preferences read-only.
- Existing API, data, privacy, and action contracts remain unchanged unless a specifically approved future scope requires a change; endpoint, schema, and storage changes are not the default. Do not infer exact visual mockups, API changes, or search-index mechanics.

## Assumptions and scope
- No exact visual mockups, API changes, or search-index mechanics are selected by this approval.
- Dashboard page information architecture and end-to-end content flows across Operation, Knowledge, and Settings, including workspace landings, navigation, progressive disclosure, summaries, and contextual detail destinations.
- Preserve all eight legacy deep links and saved start-page values/behavior without settings migration.
- Preserve existing local-only, project-scope, settings, Memory-domain, privacy, and action contracts; no additional filesystem authority.
- Out of scope: redesigning the Fieldstation shell, inventing unapproved mockups or search-index/API mechanics, changing existing contracts by default, and commit, push, release, deployment, or shipping.

## Acceptance criteria
1. At 1440x900 and 375x812, navigation exposes the three primary workspaces. Operation's landing surfaces current state and gives short direct access to worker, session, run, and workflow detail; Knowledge provides cross-source search/entry across Specs/documents, Memory, and Skills with each result labeled by source and Project/Global scope, without conflating project memory with global preferences; Settings has internal direct navigation among the existing Models, automation/workflow preference, and dashboard preference areas. Related tasks take no more than two activations from their relevant workspace landing, excluding modal and document-reading interactions. Evidence: existing UI tests and synthetic-fixture browser verification of the new workspaces.
2. Every existing capability and action remains available, and existing page paths and interaction semantics do not disappear. Preserve all eight legacy hash destinations exactly: overview, now, runs, specs, workflow, memory, skills, settings. Recognized hashes continue to take precedence over saved appearance.startPage values, and saved values/behavior remain usable without settings migration. Evidence: dashboard/web/src/App.jsx, Sidebar.jsx, Settings.jsx, and Settings tests.
3. Local-only Dashboard security and selected-project boundaries remain intact: server-side allowlisted roots, opaque project IDs and safe browser names, no browser-supplied filesystem paths, selected-project endpoints for project data, and no additional filesystem authority. ADR-033's separate existing web/workflow/Advisor settings files and formats, project-over-global resolution, source labels, and no-migration/no-overwrite behavior remain intact. Project Memory remains distinct from read-only global preferences. Existing API, data, privacy, and action contracts do not change by default. Evidence: ADR-033, ADR-041, .specs/features/dashboard/memory-domain-separation-ui.md, and source/server tests.
4. The Fieldstation shell identity remains. At 1440x900 and 375x812 there is no page-level horizontal overflow; navigation, search, and actions are touch- and keyboard-accessible, focus is visible, active navigation has correct ARIA semantics, reduced-motion behavior remains, and loading, empty, and error states truthfully reflect state. Evidence: existing UI tests and synthetic-fixture browser verification of all new workspaces and legacy deep links.
5. Before any VALIDATED status, focused tests, npm test, Dashboard production build and CLI sync, npm run check-cli, npm run specs:validate, git diff --check, and independent browser verification pass. Tests and browser verification use synthetic local data only. This TASKED record does not assert that any of these checks have run or passed.

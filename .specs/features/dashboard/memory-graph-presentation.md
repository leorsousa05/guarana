# Feature spec: Guarana dashboard Memory Graph presentation redesign

**Status: VALIDATED**

## Goal
Replace the hard-to-scan freeform Memory Graph canvas with a readable memory index and a compact automatically arranged neighborhood centered on the selected memory.

## Requirements
- Replace anonymous circle-only graph nodes and the giant freeform canvas with a readable memory index and a focused view of the selected memory's connected neighborhood. Show each memory's real title or intent and summary in readable text; show edge direction and typed relations in plain language, with incoming and outgoing directions explicit.
- On first entry, automatically select the first visible memory and show a useful neighborhood without requiring the user to choose a tiny circle or scroll through a blank plane. If filters leave no visible node, show a clear empty state. If the selected memory is filtered out, select the first visible memory or show that empty state.
- Retain the existing scope, memory-type, text, and relation filters, scope-qualified project/global identity, details, typed incoming/outgoing relations, neighbor navigation, and supersedes lineage. Keep the index as the complete bounded set currently returned by the API.
- Preserve confirmed project and global graph data and all existing relationship semantics: only confirmed project memories may be endpoints for typed project relation creation or exact relation removal; require deliberate confirmation before removal; global graph content remains read-only; do not create cross-scope edges.
- Preserve local-only project TF-IDF relationship suggestions for confirmed project candidates. Exclude the selected memory and existing relationships, show candidate score and rationale, and write nothing until the user chooses a relation type and explicitly confirms.
- Use a compact, low-card focus-centered neighborhood with automatic collision-free arrangement and the established paper/ink ledger identity. On desktop place the readable index and relationship view side by side; on mobile stack or collapse the index without page-level horizontal overflow at 375px. Keep all node text inspectable and keyboard and pointer interactions accessible.
- Remove free dragging, graph-position sessionStorage reads and writes, and the reset-layout control. Stop reading or writing the old position key without deleting or overwriting existing browser data. Remove obsolete layout or label-placement helpers only after confirming they have no other consumers.
- Do not change API contracts or payloads, backend behavior, memory vault data or schema, external-service usage, or telemetry privacy. Preserve project/global scope boundaries and do not send memory text to telemetry or external services.
- The user's explicit replacement choice for this new follow-up supersedes the previous manual drag, stored node positions, and reset-layout interaction requirement. Preserve the prior memory-relationship-management feature's historical VALIDATED status and proof unchanged; this is a separate TASKED follow-up.

## Assumptions and scope
- Retain the existing Guarana typography, colors, ledger identity, and four-tab Memory contract.
- The local selected-memory neighborhood is the primary graph view; the index contains the complete bounded node set returned by the existing API.
- Existing project/global editing, confirmation, suggestion, and privacy rules remain those recorded in the validated memory-relationship-management feature.
- Budgets follow ADR-005: worker-code 8k tokens per dispatch, worker-verify 4k tokens per dispatch, and a 32k-token / 15-minute per-run hard cap.
- Dashboard Memory Graph frontend presentation, relevant tests, and removal of graph-only obsolete layout or label helpers after consumer checks.
- No API, backend, payload, vault data/schema, external integration, commit, push, tag, publish, or shipping action.

## Acceptance criteria
1. The Graph view presents a readable memory index and a focused connected-neighborhood view. Real memory title or intent and summary text, edge direction, and typed relation wording are visible without selecting a small circle; initial entry shows the first visible memory's useful neighborhood or a clear no-match empty state, with no large blank map or anonymous-only nodes.
2. Selecting a memory from the index or neighborhood updates details and relations. Incoming and outgoing wording is unambiguous; scope, type, text, and relation filters work; selection is corrected when filtering hides its node; automatic layout avoids node and relation-label overlap. Keyboard and pointer selection and navigation have visible focus and accessible names.
3. Existing relationship behavior remains intact: only confirmed project nodes can be linked or unlinked; link types remain the existing enum; removal targets the exact selected relation and requires explicit confirmation; global nodes and edges are read-only; no cross-scope edge is possible. Suggestions use only local TF-IDF candidates among confirmed project memories, exclude the selected node and existing relations, and do not write until a human-selected type and explicit confirmation.
4. Graph no longer offers free dragging or reset-layout and does not read or write the old graph-position sessionStorage key. No unused graph-only memoryGraphLayout or label-placement code remains without a documented consumer. Existing API payloads, vault data/schema, and telemetry privacy remain unchanged; no external service is called.
5. At 375x812 and 1440x900, visible node text is readable, relation labels do not overlap, and the document has no horizontal overflow. Any scroller is labeled and contained. Desktop uses a side-by-side index and neighborhood; mobile stacks or collapses the index. Node text remains inspectable and keyboard accessible.
6. Meaningful focused Memory Graph tests and the full required checks pass: focused Memory tests, npm test, dashboard build and sync, npm run check-cli, specs validation, git diff --check, and responsive browser verification at both required viewport sizes. Independent verification records criterion-level results.

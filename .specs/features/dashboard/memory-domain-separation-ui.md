# Feature spec: Dashboard Memory domain separation UI

**Status: VALIDATED**

## Goal
Separate the Dashboard Memory UI into independent Project knowledge and User preferences workspaces while preserving project selection, global privacy, existing memory rules, and the established ledger presentation.

## Requirements
- Provide two independent first-level workspaces inside the existing Memory dashboard section, labelled Project knowledge and User preferences; do not combine both domains under the same Memory tabs or graph.
- Project knowledge contains project summary, confirmed project-only search, project-only graph and relationships, and project-only drafts with the existing scoped draft-review behavior.
- User preferences is a read-only categorized library of confirmed global preference records with text search, category and status filters, plus preference injection history. It contains no preference create, edit, or delete UI or API.
- Preserve old mixed injection records. Show global preference history in User preferences and legacy project injection events in a clearly marked historical area under Project knowledge; do not imply that project memories are newly injected.
- A small read-only API change is permitted only when required for complete global preference separation or search. Do not alter vault roots, data/schema, memory write or injection rules, or migrate records. Global preferences remain global regardless of selected project.
- Preserve the paper/ink/ledger visual identity, selected-project routing for project data, global privacy boundary, keyboard accessibility, visible focus, reduced motion, responsive layout, and no page-level overflow.
- Current API contracts: dashboard/server/routes/memory.js mounts summary, search, graph, injections, and drafts beneath the selected-project root for project-scoped data; dashboard/server/lib/memory.js summary combines project and global counts, search is project-only, graph combines project and global nodes, injections hydrates both vaults, and drafts reads the project vault only.
- Current search and projection contracts: memory/tools.js global preference search results/projections carry categories and use general for legacy category-less preferences; memorySearch is confirmed-only. The automatic-injection limit of three must not limit a dashboard library or its search. Project selector middleware remains honored by project endpoints, while the global XDG vault is invariant across project selection.
- Do not inspect or mutate actual vault contents, move/copy/reclassify records, create a new vault, change storage or schema, change write/injection policy, or introduce cross-domain text into the wrong workspace.
- No implementation, test, browser, verification, or shipping outcome is supplied or claimed by this planning record.

## Assumptions and scope
- Reversible assumption: show active/current global preferences by default; keep superseded confirmed preferences inspectable and labelled through an explicit status/filter rather than hiding stored records.
- Category-less legacy global preferences appear as general without rewriting stored records.
- Draft global preferences are excluded from the read-only active preference library.
- A dedicated read-only API may be needed to return the complete confirmed global preference set; the auto-injection limit of three is not the dashboard-library/search limit.
- Global preference injection history is scoped to global preference records; legacy project injection events remain preserved and are marked historical on the Project side.
- Global preference records remain in the existing global XDG vault and do not vary with selected project.
- Dashboard Memory workspace information architecture, project-only and preference-only presentation, read-only preference search/listing, and separated injection-history presentation.
- Small read-only API changes only when necessary for complete preference-library listing/search; focused dashboard component, CSS, server, route, app, and helper tests.
- Out of scope: vault-root, storage/schema, migration, memory write/injection rule, preference mutation, or project/global cross-domain relationship changes; inspection or mutation of actual vaults; commit, stage, push, release, or shipping.

## Acceptance criteria
1. At desktop and 375x812, the Memory section exposes distinct, keyboard-accessible first-level Project knowledge and User preferences workspaces with correct accessible names and relationships; neither workspace combines project and global domains under one tab set or graph. Proof sources: Memory.jsx, scoped CSS and component tests, plus interactive browser evidence.
2. Project knowledge shows project-only counts/summary, confirmed project-only search, project-only graph nodes/edges and relationships, and project-only drafts with the existing scoped review behavior. Changing selected project refreshes project data through the selected-project routes; the global preference vault does not change with selection. Proof sources: Memory.jsx, MemoryGraph.jsx, graph/lineage helpers, dashboard/server/lib/memory.js, memory routes/app tests, selected-project routing tests, and browser evidence.
3. User preferences lists every confirmed global preference, not merely the three records eligible for automatic injection; provides text, category, and status filters; defaults to active/current records while exposing superseded confirmed records; and displays category-less legacy preferences as general. Draft global preferences are absent. Proof sources: preference projection/search helpers, read-only API tests, fixture-backed library tests, and browser evidence.
4. Global preference injection history appears only in User preferences. Legacy project injection records remain preserved and appear only in a clearly labelled historical area under Project knowledge; presentation never implies project memories are newly injected. Proof sources: MemoryInjections.jsx, injection API/library fixture tests, and browser evidence.
5. User preferences remains read-only: all preference-library/history requests are GET-only and no create/edit/delete controls or mutation requests exist. Project knowledge and User preferences do not render each other's preference/project memory text; project historical injections remain confined to the Project historical area. Proof sources: component request-method tests, route tests, synthetic privacy fixtures, and interactive browser evidence.
6. No vault root, storage/schema, memory write/injection rule, or stored record changes occur; no record migration occurs; actual vault contents are not inspected or mutated. Any API change is read-only and limited to this separation/search. Proof sources: focused API/engine tests with temporary fixtures and source/diff review.
7. The two workspaces retain the paper/ink/ledger identity, selected-project routing, and global privacy boundary, with keyboard accessibility, visible focus, reduced-motion behavior, and no page-level horizontal overflow at 375x812 and 1440x900. Proof sources: interactive browser evidence, accessibility/keyboard checks, viewport metrics, and screenshots.
8. Focused component/CSS/server/route/app/helper tests, npm test, npm run build with CLI sync, npm run check-cli, specs validation, and git diff --check all pass. Independent worker-verify records criterion-level results and interactive browser evidence at 375x812 and 1440x900. Proof sources: exact command output, proof report/screenshots, and independent verification; no browser criterion is considered passed before that evidence exists.
